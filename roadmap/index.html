AI Engineer Roadmap what a hiring manager actually checks

Most roadmaps tell you what to study. This one also tells you what I look for when your CV lands on my side of the table. Seven stages, the signals I check at each one, and free resources only.

R

I'm Rahul. I studied mechanical engineering in India, switched to software in 2016, did a Master's in Germany, and went from engineer to senior to Engineering Manager over 10+ years in software.

I screen CVs and sit on interview panels. I also worked on AI as a student developer, before ChatGPT made it a headline.

Honest version? Everything under "What I check" is my view, from the interviews I've been part of. It is not a rule for every company, and no roadmap, including this one, can promise you a job.

The roadmap, in seven stages

Go roughly in order. Stages 5 to 7 overlap in real life: you will build, deploy and evaluate in loops. Don't wait to "finish" a stage before you build something.

  1. 1

    Fundamentals: how software actually runs

    Programming basics, data structures, the terminal, Git, how HTTP and the web work, and enough complexity thinking to know why your loop is slow.

    What I check
    • A Git history that looks like real work: small commits, messages a teammate could read.
    • Can you explain one bug you fixed, step by step, without the word "somehow"?
    • In the interview: can you say what your own code costs in time and memory? I care more about that than a memorised puzzle answer.
    Free resources
    • Harvard CS50xIntro to computer science, free online
    • MIT: The Missing SemesterShell, Git, editors, debugging
    • Pro Git (official book)Read chapters 1 to 3 first
  2. 2

    Python + one backend framework

    Python properly (functions, classes, typing, virtual environments, tests), then ONE framework, FastAPI or Django, until you can build a small API from an empty folder.

    What I check
    • One API you built yourself: input validation, error handling, a few tests. One done well beats three frameworks listed.
    • Clean basics: pinned dependencies, a README that runs, no secrets in the repo.
    • Can you read code you didn't write and tell me what it does? Most of the job is that.
    Free resources
    • The official Python tutorialpython.org
    • FastAPI tutorialOfficial docs, step by step
    • Django tutorialOfficial docs, if you pick Django
  3. 3

    Data and SQL

    SQL (joins, group by, indexes), one real database like PostgreSQL, and pandas for cleaning messy data. AI work is mostly data work wearing a nicer jacket.

    What I check
    • Can you write a join with a group by on a whiteboard, roughly right, without panic?
    • Do you know what an index is and when a query needs one?
    • In your project: where did the data come from, what was wrong with it, and what did you do about it?
    Free resources
    • PostgreSQL tutorialOfficial docs, part I
    • Kaggle Learn: Intro to SQLFree, exercises need a free account
    • pandas: getting startedOfficial docs
  4. 4

    Machine learning basics

    Train, validation and test splits, baselines, overfitting, the common metrics, and a few classic models with scikit-learn. You don't need to derive every formula. You do need to know when a number is lying to you.

    What I check
    • Did you start with a simple baseline before the fancy model? Tell me how much the fancy one actually beat it by.
    • Do you know why 95% accuracy can be useless on imbalanced data, and which metric you'd use instead?
    • Can you explain overfitting and data leakage in plain words, with an example from your own work?
    Free resources
    • Google Machine Learning Crash CourseFree, from Google
    • scikit-learn: getting startedOfficial docs
    • fast.ai: Practical Deep LearningFree course, code first
  5. 5

    LLM apps: APIs, RAG, evals, agents

    Calling a model API with structured output, retrieval-augmented generation (RAG), writing evaluations, and agents that use tools. This is the part everyone rushes to. It goes much better after stages 1 to 4.

    What I check
    • My favourite question: when does it give a wrong answer, and how did you catch it? If you have a test set with expected answers, that already tells me a lot.
    • API basics done right: timeouts, retries, rate limits, and you know roughly what a request costs.
    • For RAG: how you chunk, how you know retrieval found the right passage, and what you changed when it didn't.
    • For agents: did you try the simplest version first? Knowing when NOT to build an agent is a good sign.
    Free resources
    • Hugging Face LLM CourseFree course: models, fine-tuning, apps
    • Building effective agentsAnthropic engineering write-up
    • Define success and build evalsOfficial Claude docs
  6. 6

    Deployment, cloud and MLOps basics

    Docker, one cloud or free hosting option, environment variables and secrets, logs, and the basics of keeping a model in production: versioning, monitoring, what happens when an API is down.

    What I check
    • Does it run anywhere other than your laptop? A link I can open is worth more than a screenshot.
    • Secrets in environment variables, not in the code. Assume someone will open your repo.
    • Can you tell me what you'd watch after launch: errors, latency, cost, and answers getting worse over time?
    Free resources
    • Docker: get startedOfficial docs
    • Made With MLFree MLOps course, design to production
    • Google: Rules of Machine LearningShort, practical, still holds up
  7. 7

    One portfolio project that proves it

    Pick a real problem (yours, a friend's, a small business near you), build it end to end with stages 2 to 6, deploy it, and measure it. One, done properly.

    What I check
    • A README with: the problem, what you built, a live link, how you evaluated it, and what failed.
    • One number you moved on your own test set, with the "before" and "after".
    • You can defend every part in the interview. Using AI to write code is fine. Not understanding the code it wrote is not.

    My verdict: one deployed project beats ten certificates.

How I read your CV

Your CV gets seconds, not minutes. One recruiter eye-tracking study (Ladders, 2018) measured an average of 7.4 seconds on the first screen. It is one company's study and doesn't say how many recruiters took part, so treat it as an average, not a rule. Here's what I look at in that time. My practice, not a law.

1The role at the top. Does it match the job, in plain words?
2One result you moved, with its number. What changed because you were there?
3A link to something you built and deployed, that I can actually open.

Honest version? The long skills list with 30 tools in it, I usually skip. It tells me what you've heard of, not what you've done.

Hard to judge

Built an AI chatbot using Python, LangChain, OpenAI, RAG, vector DB.

Easy to judge

Built a RAG assistant for a college FAQ; correct answers on my 50-question test set went from 31 to 42 after I changed chunking; live demo + repo linked.

The second line is an example of the shape, not a real candidate. The study: Ladders eye-tracking study 2018, reported by HR Dive (8 Nov 2018).

Verdict:proof in the first two lines.

Mistakes I see

Patterns from the CVs and interviews I've seen. Every one of them is fixable.

  1. Ten certificates, zero deployed projects.A certificate says you finished a course. A deployed project says you finished something nobody asked you to.
  2. A skills list with every tool, and proof of none.Pick the three you'd happily be grilled on. Remove the rest or move them to the bottom.
  3. Jumping to agents before you can write a SQL join.The fancy part sits on boring parts. Interviews test the boring parts.
  4. "It works" with no test set.If you never measured it, you don't know when it's wrong. Neither do I.
  5. The unchanged tutorial project.Tutorials are fine for learning. On a CV, show what you changed, what broke and what you added.
  6. API keys committed to GitHub.I notice. So do bots that scan public repos for keys.
  7. Code you can't explain.Use AI as much as you like. In the interview, it's just you and the code.
